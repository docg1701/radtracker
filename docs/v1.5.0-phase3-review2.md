### Fixed

1. **Missing `@st.fragment` on `render_chat_tab`**  
   **Location:** `src/ui/chat.py:20`  
   **Issue:** The plan explicitly required fragment isolation to mitigate high-impact conflicts between `st.rerun()` and streaming. Without it, every chat interaction (user input, pill click, stream completion, button click) reran the entire app, causing sidebar + all tabs to re-execute.  
   **Resolution:** Added `@st.fragment` decorator above `render_chat_tab`. Verified that nested `st.rerun()` calls from `_render_suggestion_chips`, `_render_action_buttons`, and the dispatcher are all inside the fragment scope and therefore trigger fragment-local reruns.

2. **No empty-state UX when `active_mods` is empty**  
   **Location:** `src/ui/chat.py:38–42`  
   **Issue:** If the user had an API key configured but zero active modalities, the chat tab rendered a blank message area with only the chat input and buttons, offering no hint about what to do.  
   **Resolution:** Added an early-return branch with `_render_chat_empty_state` that mirrors the existing API-key empty state: centered card with `:material/smart_toy:` icon and instructions to go to Configuração.

3. **`_trim_history()` lacks defensive guard for missing/corrupted system message**  
   **Location:** `src/ui/chat.py:204–216`  
   **Issue:** R1 noted this but left it unfixed. If `messages` were empty or `messages[0]` were not a system message (e.g., corrupted state), `_trim_history` would either crash on `messages[0]` access or silently treat a user message as the system prefix.  
   **Resolution:** Added guard clause (`if not messages or messages[0].get("role") != "system": return`) as the first line of `_trim_history`.

4. **`_stream_response()` catches only `LLMUnavailableError`**  
   **Location:** `src/ui/chat.py:126–141`  
   **Issue:** Any unexpected exception raised by `st.write_stream` (e.g., `StreamlitAPIException` from a malformed stream, or a bug in the generator) would propagate uncaught and crash the app.  
   **Resolution:** Added a broad `except Exception as exc:` fallback that renders a user-friendly error bubble inside the assistant chat message, stores the error text as the assistant response (so the conversation remains visible), and prevents the crash.

5. **`_trigger_initial_report()` duplicated cache-key logic and exceeded 20 lines**  
   **Location:** `src/ui/chat.py:88–110`  
   **Issue:** The function mixed JSON serialisation, cache lookup, stats computation, and prompt building in one block, making it 24 lines and violating the project’s 4–20 line function guideline.  
   **Resolution:** Extracted `_build_historical_cache_key()` helper (`chat.py:66–77`). `_trigger_initial_report` now focuses on orchestration and is under 20 lines.

6. **`st.chat_input` missing explicit key**  
   **Location:** `src/ui/chat.py:61–63`  
   **Issue:** Although there is only one chat input in the app, the deep-dive flagged key absence as a potential memory/performance risk.  
   **Resolution:** Added `key="chat_input_main"`.

### Warning

- **OpenRouter SSE error JSON silently swallowed in backend (`src/llm_client.py`).** If OpenRouter returns HTTP 200 with an SSE chunk like `{"error": {"message": "rate limited"}}`, `generate_stream()` ignores it (no `choices` key → falls back to `[{}]`), yields zero tokens, and raises `LLMUnavailableError("Resposta vazia do modelo")`. The chat user sees a generic “empty response” instead of the real error. This is outside the direct frontend scope but directly impacts chat UX. **Recommended fix:** In `generate_stream`, after `json.loads(data_str)`, check for `data.get("error")` and raise `LLMUnavailableError(error_message)` before inspecting `choices`.
