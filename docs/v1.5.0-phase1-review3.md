### Correct (what was already good)

- **Plan compliance — payload structure:** `_build_payload()` correctly sets `"model"`, `"messages"`, `"stream"`, `"max_tokens": 800`, and `"temperature": 0.3`. Verified against plan §6.
- **Plan compliance — `[DONE]` terminator:** `data_str.strip() == "[DONE]"` matches the plan and tolerates leading/trailing whitespace.
- **Plan compliance — safe SSE parser:** The current parser (`choices = data.get("choices") or [{}]`, etc.) is actually *safer* than the naive `data.get("choices", [{}])[0].get("delta", {})` pattern shown in the plan. It correctly handles `choices: []`, `choices: [null]`, `delta: null`, and missing fields without crashing.
- **`build_rag_context` public API:** Signature, return type (`str`), and integration contract (`messages.insert(0, {"role": "system", "content": result})`) are all correct.
- **Token streaming mechanics:** `response.iter_lines()` properly buffers across HTTP chunk boundaries, so tokens are never lost due to network fragmentation. SSE blank lines between events are skipped naturally.
- **Connection-drop mid-stream:** `httpx.stream()` context manager ensures the connection is closed. Any read failure raises `httpx.HTTPError`, which is caught and wrapped as `LLMUnavailableError`.
- **`st.write_stream()` integration:** The generator raises `LLMUnavailableError` on all fatal paths, which the planned `chat.py` dispatcher catches in its `try/except LLMUnavailableError` block.
- **Real-world OpenRouter behavior:** Lines without `choices` (metadata, pings) are ignored. Final chunks with `finish_reason: "stop"` and empty `delta` are skipped correctly.

### Fixed (issues found and resolved)

#### BLOCKER #1 — `generate()` returns `None` when API sends `content: null`
**Location:** `src/llm_client.py`, `generate()` return statement  
**Evidence:** `return data["choices"][0]["message"]["content"]` returns Python `None` when OpenRouter JSON contains `"content": null` (content filtering, model refusal, etc.). The return type is annotated `-> str`, so downstream code expecting a string receives `None`, causing `TypeError` on string operations.
**Fix:** Added defensive extraction:
```python
try:
    content = data["choices"][0]["message"]["content"]
except (KeyError, IndexError, TypeError) as exc:
    raise LLMUnavailableError(f"Resposta inesperada da API: {exc}") from exc
if not isinstance(content, str) or not content.strip():
    raise LLMUnavailableError("Resposta vazia ou bloqueada pelo modelo")
return content
```
**Regression test:** `test_llm_client_empty_content_200`

#### BLOCKER #2 — `generate()` fragile response parsing leaks raw exceptions
**Location:** `src/llm_client.py`, `generate()`  
**Evidence:** If the API returns JSON missing `choices` or `message` keys, `data["choices"][0]["message"]["content"]` raises `KeyError` or `IndexError`. These were caught only by the broad `except Exception` at the bottom, producing an unhelpful raw exception string like `"'choices'"` instead of a meaningful user-facing message.
**Fix:** Isolated response extraction in its own `try/except` block with explicit `(KeyError, IndexError, TypeError)` handling, wrapped as `LLMUnavailableError("Resposta inesperada da API: ...")`.
**Regression test:** `test_llm_client_missing_choices`

#### WARNING #1 — `generate()` connection errors use raw messages, inconsistent with `generate_stream()`
**Location:** `src/llm_client.py`, `generate()` exception handling  
**Evidence:** `generate_stream()` had a dedicated `except httpx.HTTPError` handler producing `"Erro de conexão com OpenRouter: {exc}"`. `generate()` only caught `TimeoutException` and `HTTPStatusError`; everything else fell into `except Exception`, so a `ConnectError` produced `[Errno 111] Connection refused` instead of the friendly message.
**Fix:** Added `except httpx.HTTPError as exc` handler to `generate()` with the same message pattern as `generate_stream()`.
**Test:** `test_generate_stream_network_error` (verifies streaming side); existing `generate()` error tests still pass.

#### WARNING #2 — `generate_stream()` silently yields nothing on empty SSE responses
**Location:** `src/llm_client.py`, `generate_stream()`  
**Evidence:** If OpenRouter returns a 200 with an empty body, only `data: [DONE]`, or an unexpected format (e.g., HTML from a proxy with 200 status), the generator would loop zero times or skip all lines and exit cleanly. `st.write_stream()` would return `""`, and `chat.py` would append a blank assistant bubble to history. No error is raised, so the user sees a silent failure.
**Fix:** Added `yielded_any = False` flag. Set to `True` on each valid token yield. After the stream loop, if no tokens were yielded, raise `LLMUnavailableError("Resposta vazia do modelo")`.
**Regression tests:** `test_generate_stream_empty_response`, `test_generate_stream_malformed_sse`

#### WARNING #3 — `headers` dict duplicated across both methods
**Location:** `src/llm_client.py`, `generate()` and `generate_stream()`  
**Evidence:** Both methods inlined the same `{"Authorization": ..., "Content-Type": ...}` dict.
**Fix:** Extracted `LLMClient._headers() -> dict[str, str]` private helper. Both methods now call `self._headers()`.

### Note (observations, no code change)

- **`_SYSTEM_PROMPT` hardcodes "Galvani" while settings module uses `{user_name}` interpolation.** `src/ui/settings.py` has `_DEFAULT_LLM_PROMPT` with a `{user_name}` placeholder that gets interpolated during settings load. `src/llm_client.py`'s `_SYSTEM_PROMPT` is a near-duplicate but hardcodes the name. Since `chat.py` is supposed to always pass a custom prompt from `st.session_state.llm_prompt`, this fallback rarely fires, but it is a minor architecture drift.

- **`_SYSTEM_PROMPT` tone is one-shot oriented.** The prompt says "Analise os dados de produção abaixo e produza uma análise completa e detalhada." This is appropriate for the legacy one-shot `generate()` but slightly directive for a conversational chat fallback. Not a blocker because `chat.py` is designed to pass its own prompt.

- **`build_rag_context` docstring says "Se None"** but the implementation uses `system_prompt or _SYSTEM_PROMPT`, so an empty string `""` also falls back to the default. Very minor doc imprecision.
