## Applied Fixes

### 1. BLOCKER (robustness): SSE parsing could crash on `null` delta or choice — `AttributeError` not caught
**Location:** `src/llm_client.py:316` (original line `data.get("choices", [{}])[0].get("delta", {})`)

The `.get()` chain `data.get("choices", [{}])[0].get("delta", {})` is **not** safe when the API returns `null` inside the structure, e.g.:

```python
{"choices": [{"delta": null}]}
# → None.get("content") → AttributeError

{"choices": [null]}
# → None.get("delta", {}) → AttributeError
```

The original `except (json.JSONDecodeError, KeyError, IndexError)` did **not** catch `AttributeError` (or `TypeError`), so a single malformed SSE line would crash the entire stream generator and propagate to the Streamlit UI.

**Fix applied:**
- Replaced the unsafe chain with explicit null-guarded steps:
  ```python
  choices = data.get("choices") or [{}]
  choice = choices[0] if choices else {}
  delta = (choice or {}).get("delta") or {}
  ```
- Added `AttributeError` and `TypeError` to the per-line exception tuple so *any* malformed line is skipped gracefully.

### 2. WARNING (spec accuracy): `build_rag_context` docstring falsely claimed `user_name` interpolation
**Location:** `src/llm_client.py:92–98`

The docstring stated:
> "Se None, usa o default interpolado com user_name."

This was incorrect. The function has no `user_name` parameter and `_SYSTEM_PROMPT` contains the hardcoded string `"Galvani"`. The actual interpolation (`{user_name}` → real name) happens upstream in `src/ui/settings.py` when `llm_prompt` is loaded into `st.session_state`. When `chat.py` passes `st.session_state.llm_prompt` to `build_rag_context`, interpolation is already done; when it passes `None`, the hardcoded fallback is used verbatim.

**Fix applied:**
- Corrected the docstring to:
  > "Se None, usa o prompt padrão (_SYSTEM_PROMPT)."

## Additional Findings

### 3. WARNING: `generate_stream()` lacked broad exception fallback present in `generate()`
**Location:** `src/llm_client.py:332–346` (after fix)

`generate()` ends with `except Exception as exc:` to wrap any unexpected failure in `LLMUnavailableError`. The original `generate_stream()` only caught `httpx` exceptions, meaning a non-HTTP bug (e.g., unexpected response iterator behavior) would bubble up as a raw Python exception instead of the `LLMUnavailableError` the chat UI expects.

**Fix applied:**
- Added `except Exception as exc:` at the end of `generate_stream()` for parity with `generate()`.

### 4. NOTE: `_SYSTEM_PROMPT` is duplicated with `_DEFAULT_LLM_PROMPT` in `settings.py`
**Location:** `src/llm_client.py:37` and `src/ui/settings.py:_DEFAULT_LLM_PROMPT`

Both modules define the same prose prompt. `settings.py` keeps the template form with `{user_name}`; `llm_client.py` keeps the compiled form with `"Galvani"`. This is architectural drift — a single shared constant (or importing the template and compiling it) would prevent them from going out of sync. Not a blocker for Phase 1, but worth a cleanup ticket.

### 5. NOTE: `generate()` still uses unsafe dict access for the non-streaming response
**Location:** `src/llm_client.py:296`

```python
return data["choices"][0]["message"]["content"]
```

This is existing (pre-v1.5.0) code and is rescued by the broad `except Exception`, so it does not crash the app. However, it produces a generic `LLMUnavailableError` instead of a specific "unexpected response format" message. Since the first reviewer approved backward compatibility and this is not new streaming code, it is noted but left untouched.
